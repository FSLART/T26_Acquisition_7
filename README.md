# T26_Acquisition_7

Firmware for **Acquisition board 7 (AQT7)** of the T26 car. It runs on an
**STM32F412RET6** and:

- measures **rear brake pressure**, **left/right suspension travel** and **coolant temperature** (NTC) with the ADC,
- receives **front brake pressure** from another node over CAN,
- drives the **brake light** from the front and rear pressures,
- publishes the measurements on two CAN buses (Autonomous and DATA),
- prints a human-readable log on UART and exposes a debug snapshot (`acq7`) for STM32CubeIDE Live Expressions.

The project is generated and built with **STM32CubeIDE** (`T26_Acquisition_7.ioc`). All application code lives
in `USER CODE` blocks, so the project can be regenerated from CubeMX without losing it.

The firmware is being ported to **Zephyr RTOS** (`zephyr_app/`). The port already measures, filters and
publishes every sensor, drives the brake light and runs the watchdog; see [Zephyr firmware](#zephyr-firmware)
for how it is organised and what is still missing. To set up a Zephyr development environment, see
[Zephyr development setup](#zephyr-development-setup).

| PB12 / PB13 | CAN2 RX / TX | DATA bus |

| Peripheral | Configuration |
|---|---|

## Program flow

After the CubeMX init, `main()` starts TIM7 and the ADC DMA, clears the moving-average buffers and enters a
cooperative scheduler driven by `time_ms` (TIM7):

| Period | Function | Work |
|---|---|---|
| every loop | `execute_immediate_tasks()` | (empty) |
| 10 ms | `execute_10ms_tasks()` | Refresh watchdog, latch filtered ADC values, `CAN_Service()` on both buses, update the `acq7` debug snapshot |
| 50 ms | `execute_50ms_tasks()` | Update ADC moving average, convert all sensors, send rear pressure on CAN1 `0x770`, compute front pressure / timeout, drive the brake light |
| 100 ms | `execute_100ms_tasks()` | Toggle heartbeat, `printf` all readings on UART |
| 125 ms | `Data_SendSensors()` | Send `AQT7` (suspension + NTC) on CAN2 at 8 Hz |

CAN reception is interrupt-driven (`HAL_CAN_RxFifo0MsgPendingCallback`).

### ADC filtering

The DMA continuously refreshes `ADC_VALUE[]` (`[0]` brake, `[1]` susp left, `[2]` susp right, `[3]` NTC1).
Every 50 ms `ADC_UpdateMovingAverage()` pushes the latest sample of each channel into a 10-entry circular
buffer and stores the mean in `adc_filtered[]`. The filter therefore spans **500 ms**.

## Sensors

### Brake pressure (rear) – `MeasureBrakePressure()`

- Sensor: **Bosch 0 261 545 053**, gauge pressure, 0.5–4.5 V for 0–140 bar, 5 V supply.
- PA7 sees the sensor output ~1:1 (`CONVERSION_FACTOR = 1.0`).
- Conversion:
  `V = adc × 3.3 / 4095`
  `p = (V − OFFSET_VOLTAGE) / 0.02857 V/bar`, clamped to 0…140 bar.
- `OFFSET_VOLTAGE = 0.614 V` is the PA7 voltage measured with the pedal released (nominal would be 0.5 V).
  It has drifted before; to re-zero, read `acq7.adc.volts[0]` at rest in Live Expressions and copy the value here.

> **Limitation:** the ADC saturates at 3.3 V ≈ **98 bar**, and above that PA7 exceeds its 3.6 V absolute
> maximum. A divider must be added and its ratio set in `CONVERSION_FACTOR` before relying on higher pressures.

### Brake pressure (front) – received on CAN1

- Received in `HAL_CAN_RxFifo0MsgPendingCallback` from ID **`0x710`** (standard), bytes 0–1 little-endian,
  **0.1 bar/bit** (`coded_front_pressure`).
- The value is trusted only while frames keep arriving: if no `0x710` is seen for
  `FRONT_PRESSURE_TIMEOUT_MS` (500 ms), `BRK_PRESS_FRONT` is forced to 0 and `front_alive` = 0.

### Brake light

Every 50 ms, PC10 is driven **LOW** (light on) if
`BRK_PRESS_REAR ≥ PRESSURE_LEVEL_REAR` **or** `BRK_PRESS_FRONT ≥ PRESSURE_LEVEL_FRONT` (both 7 bar),
and HIGH otherwise. If the front pressure frame is lost, the light follows the rear pressure only.

### Suspension – `MeasureSuspensionPosition()`

- Sensor: linear potentiometer, **75 mm** electrical stroke, 5 V supply, scaled to 3.3 V by a divider on the board.
- Absolute position: `pos_mm = 75 × V_sensor / 5`, with `V_sensor = V_pin / (3.3 / 5)`.
- **Ride-height zeroing:** the first time the moving-average buffer is full (~500 ms after boot) the absolute
  positions are stored in `SUSP_LEFT_ZERO` / `SUSP_RIGHT_ZERO` and `susp_zeroed` is set. Until then 0 mm is sent.
  The car must therefore be at rest on its wheels at power-up.
- Reported value: `SUSP_x = SUSP_x_ZERO − pos_mm`
  - **positive = extension** (wheel drops)
  - **negative = compression** (wheel rises)
  - (on this car the sensor voltage drops when the suspension extends, hence the subtraction order)

### Coolant temperature (NTC) – `MeasureNtcTemperature()`

- Sensor: **Vishay NTCAIMM66H**, 10 kΩ @ 25 °C, B25/85 = 3984 K.
- Board circuit: `5 V → NTC → node A`; node A has 100 kΩ to GND and a 24.3 kΩ / 4.9 kΩ divider down to the ADC pin.
- Conversion:
  1. `V_A = V_pin × (24.3k + 4.9k) / 4.9k`
  2. `R_low = 100k ∥ (24.3k + 4.9k)`
  3. `R_ntc = R_low × (5 V − V_A) / V_A`
  4. Beta equation: `1/T = 1/298.15 + ln(R_ntc / 10k) / 3984`, result in °C
- Fault detection: ADC = 0 (open sensor) or `V_A ≥ 5 V` (shorted sensor) returns `NTC_FAULT_C` (−99 °C).
- `NTC_VSUPPLY` (5.0 V) should be tuned to the real 5 V rail for best accuracy.
- Only one NTC is fitted (`NTC_COUNT = 1`). Adding more requires new ADC ranks in the `.ioc`, raising
  `NTC_COUNT`, and adding signals to the DBC and `Data_SendSensors()` (a `_Static_assert` enforces this).

## CAN interface

Both buses run at 1 Mbit/s with standard (11-bit) IDs.

### CAN1 – Autonomous bus

| Dir | ID | DLC | Period | Content |
|---|---|---|---|---|
| RX | `0x710` | ≥2 | (sender) | Front brake pressure, bytes 0–1, uint16 LE, 0.1 bar/bit |
| TX | `0x770` | 2 | 50 ms | Rear brake pressure, bytes 0–1, uint16 LE, 0.1 bar/bit |

The CAN1 hardware filter (bank 0) only accepts `0x710`.

### CAN2 – DATA bus

| Dir | ID | Name | DLC | Period |
|---|---|---|---|---|
| TX | `0x770` | `AQT7` | 8 | 125 ms (8 Hz) |

`AQT7` is packed with the generated `data_t26_aqt7_pack()`:

| Signal | Bytes | Type | Scale | Unit | Notes |
|---|---|---|---|---|---|
| `SUSP_L` | 0–1 | int16 LE | 0.1 | mm | + extension / − compression |
| `SUSP_R` | 2–3 | int16 LE | 0.1 | mm | + extension / − compression |
| `NTC_1` | 4 | uint8 | 1 | °C | Rounded, clamped to 0…254; **255 = sensor open/shorted** |
| — | 5–7 | — | — | — | Unused (0) |

CAN2 accepts all IDs in hardware (bank 18), but RX notification is not enabled, so nothing is read from it.

### Filter banks

The two controllers share filter banks. `CAN_SLAVE_START_BANK = 18` assigns banks 0–17 to CAN1 and 18–27 to CAN2.
Because HAL rewrites the shared `FMR` register on every `HAL_CAN_ConfigFilter()` call, every filter config must use
the same `SlaveStartFilterBank` value.

### Transmission (`CAN_Send`)

- Non-blocking and never calls `Error_Handler()`.
- Sends **only the latest value**: any older copy of the same ID still pending in a TX mailbox is aborted first,
  so stale data never queues up.
- If all three mailboxes are busy the value is dropped (counted in `tx_dropped`); the next period sends a fresh one.

### Bus health (`CAN_Service`)

Called every 10 ms per bus. It polls `ESR`/`TSR` and the HAL error code and fills `can1_status` / `can2_status`
(`CAN_BusStatus`):

- `state` / `state_text`: OK, WARNING (TEC/REC ≥ 96), PASSIVE (≥ 128), BUS_OFF, NOT_STARTED
- `tec`, `rec`: error counters
- `last_error` / `last_error_text`: last protocol error (stuff, form, ACK, bit, CRC) with a description of the usual causes
- `errors.*`: per-type counters, bus-off count, arbitration-lost and TX error counts
- `error_last`, `error_seen`: HAL error flags as named bit-fields (write 0 to `error_seen.raw` to clear)
- `tx_queued`, `tx_dropped`, `tx_aborted`, `restarts`, `fault`, `fault_count`

State/error changes are printed on UART (at most once per second per bus). If a controller is not running
(e.g. it failed to start because the transceiver was unpowered), it is re-initialised in place at most every
100 ms. Bus-off is recovered automatically by hardware (`AutoBusOff = ENABLE`).

A missing or faulty CAN bus never stops the firmware.

## Debugging

### Live Expressions

Add **`acq7`** to STM32CubeIDE Live Expressions to see the whole board, refreshed every 10 ms:

| Field | Contents |
|---|---|
| `acq7.time_ms` | Uptime |
| `acq7.adc.raw[]`, `.filtered[]`, `.volts[]` | Per channel: DMA sample, moving average, pin voltage |
| `acq7.sensors.*` | `brake_rear_bar`, `brake_front_bar`, `susp_left_mm`, `susp_right_mm`, `ntc_c[]` |
| `acq7.io.brake_light`, `.heartbeat` | Output pin levels (brake light 0 = on) |
| `acq7.front.*` | Raw `0x710` value, `alive`, `age_ms`, `rx_count` |
| `acq7.can.tx_770_autonomous`, `.tx_aqt7_data` | Last payloads queued on each bus |
| `acq7.can.autonomous`, `.data` | Full `CAN_BusStatus` of CAN1 and CAN2 |

### UART

USART1 (PA9, 115200 8N1) prints every 100 ms (messages are in Portuguese; the values below are only examples):

```
A pressao traseira é 0.00 bar e adc é 762
A pressao da frente é 0.00 bar e 0
A suspensao esquerda é 0.00 mm e adc é 2048
A suspensao direita é 0.00 mm e adc é 2050
A NTC1 está a 24.8 C e adc é 1234
```

plus `CAN1 (AUTONOMOUS) ...` / `CAN2 (DATA) ...` lines when a bus state or error changes.

`printf` uses blocking `HAL_UART_Transmit`, so each 100 ms report takes a few tens of ms of CPU time at 115200 baud.

### Heartbeat

PC11 toggles every 100 ms (5 Hz blink) while the main loop is running. If the loop stalls for ~2 s the IWDG resets the MCU.

### Regenerating the DBC code

`Core/DBC/*.c/h` are generated by cantools from the T26_DBC repository and **updated automatically by a
workflow**. Don't edit them by hand: changes are overwritten on the next update. Both the STM32CubeIDE build
and the Zephyr port use these files from this folder. If `AQT7` changes, update `Data_SendSensors()` in
`main.c` (STM32CubeIDE) and the encoders in `zephyr_app/src/can_tx.c` (Zephyr) accordingly.

## Zephyr firmware

The Zephyr port in `zephyr_app/` replaces the CubeIDE super-loop (`execute_10ms_tasks()`,
`execute_50ms_tasks()`, ...) with one thread per job. Each module owns its data and its lock; other modules
only read it through a getter, so no thread ever reads a half-updated value.

### Modules

| File | Job | Public API |
|---|---|---|
| `main.c` | Starts the watchdog, sets up the hardware in order, starts the threads, then every 100 ms toggles the heartbeat, feeds the watchdog and runs the CAN health check | — |
| `app.h` | Thread priorities and stack sizes shared by the modules | `PRIO_*`, `STACK_SIZE_*` |
| `conversions.c/.h` | ADC counts → bar, mm, °C. Plain C with no Zephyr calls, so it can be unit tested on the PC | `MeasureBreakPressure()`, `MeasureSuspensionPosition()`, `MeasureNTCTemperature()`, `NTC_FAULT_C` |
| `sensors.c/.h` | ADC1 sampling, moving average, suspension zeroing, conversion | `sensors_init()`, `sensors_start()`, `sensors_get()`, `struct vehicle_sensor_data` |
| `brake_light.c/.h` | PC10 brake light from the rear and front pressures | `brake_light_init()`, `brake_light_start()` |
| `can_bus.c/.h` | Both CAN controllers: start, RX filters, RX queue, non-blocking send, counters, bus health (error types, log, restart). Knows nothing about the DBC | `can_bus_init()`, `can_send_frame()`, `can_bus_receive()`, `can_bus_service()`, `can_bus_get_status()`, `can_bus_name()`, `can_stats[]` |
| `can_rx.c/.h` | List of frames to receive, DBC decoding, front brake pressure | `can_rx_ids[]`, `can_rx_start()`, `get_front_brake_pressure()`, `get_front_brake_status()` |
| `can_tx.c/.h` | DBC encoding and send schedule of every periodic frame | `can_tx_start()`, `can_tx_get_last_payloads()` |
| `watchdog.c/.h` | IWDG supervisor: feeds only while every thread is alive | `watchdog_init()`, `watchdog_register()`, `watchdog_checkin()`, `watchdog_service()`, `watchdog_fail()` |
| `debug.c/.h` | `acq7` debug snapshot for the debugger, periodic sensor log | `acq7`, `debug_start()` |
| `../Kconfig` | App options settable in `prj.conf` (`CONFIG_AQT7_DEBUG_PRINT_MS`) | — |

Each `.c` registers its own log module (`sensors`, `can_bus`, `can_rx`, ...), so every log line shows where it
came from.

### Threads

| Thread | Priority | Period | Job |
|---|---|---|---|
| `main` | 0 (Zephyr default) | 100 ms | Heartbeat (PC11) + `watchdog_service()` + `can_bus_service()` |
| `sensors` | 2 | 10 ms | Read the 4 ADC channels, average, convert, publish |
| `brake_light` | 3 | 50 ms | Light on while rear **or** front pressure ≥ 7 bar |
| `can_rx` | 4 | event, ≤ 100 ms | Decode received frames (waits at most 100 ms so it can check in with the watchdog) |
| `can_tx` | 5 | 50 ms / 125 ms | CAN1 0x770 every 50 ms, CAN2 AQT7 every 125 ms |
| `debug` | 6 | 10 ms | Refresh `acq7`; log the sensor values every `CONFIG_AQT7_DEBUG_PRINT_MS` |

A lower number runs first. All threads use absolute deadlines (`K_TIMEOUT_ABS_MS`), so their periods don't
drift with the time spent in the loop.

Threads are defined with `SYS_FOREVER_MS` as start delay: they exist from boot but only run once `main` calls
their module's `*_start()`.

### Start-up and failure handling

1. `watchdog_init()` starts the IWDG first, so a hang anywhere in the setup also resets the board.
2. The heartbeat GPIO, `sensors_init()`, `brake_light_init()` and `can_bus_init()` set up the hardware.
3. If any of them fails, `watchdog_fail()` logs the reason and stops feeding: the IWDG resets the board after
   2 s and the whole setup is tried again. This matches the CubeIDE firmware (`Error_Handler` + IWDG). A
   permanently broken part (e.g. an unpowered CAN transceiver) therefore makes the board reboot every ~2 s.
4. The five threads are started; each registers with the watchdog.

### Watchdog

- IWDG on the LSI, **2000 ms** timeout (same as the CubeIDE firmware: prescaler 64, reload 1000).
- Every thread calls `watchdog_checkin()` once per loop. `main` feeds the IWDG every 100 ms, but **only if
  every registered thread checked in** since the last feed. A single hung thread therefore resets the board,
  not only a hung main loop.
- After 1 s without a feed, the log names the thread that stopped (`Thread can_tx stopped checking in`),
  before the reset at 2 s.
- The IWDG is paused while a debugger halts the CPU, so breakpoints don't reset the board.

To supervise a new thread: add it to `enum watchdog_client` and `client_name[]` in `watchdog.c`, call
`watchdog_register()` in its `*_start()` and `watchdog_checkin()` in its loop. Its loop must never block for
more than ~1 s.

### Sensor data

`sensors.c` samples all four channels every **10 ms** and keeps a **10-sample moving average** per channel
(100 ms window). Each sample it publishes a `struct vehicle_sensor_data`:

| Field | Unit | Notes |
|---|---|---|
| `rear_brake_bar` | bar | `MeasureBreakPressure()` |
| `susp_left_mm`, `susp_right_mm` | mm | Relative to ride height: + extension, − compression. 0 until zeroed |
| `ntc1_c` | °C | `NTC_FAULT_C` (−99) for an open or shorted sensor |
| `raw[4]` | ADC counts | Latest sample per channel, for debugging |
| `filtered[4]` | ADC counts | Moving average per channel, for debugging |

The ride height is the first full average after boot (~100 ms; the CubeIDE firmware waited ~500 ms). It is
logged as `Suspension zeroed: L ... mm, R ... mm`.

Other modules read a consistent copy with `sensors_get()`:

```c
#include "sensors.h"

struct vehicle_sensor_data d = sensors_get();
if (d.rear_brake_bar >= 7.0f) { ... }
```

The front brake pressure comes from CAN, so it lives in `can_rx.c` and is read with
`get_front_brake_pressure()`. It returns 0 if 0x710 never arrived or is older than 500 ms.

The ADC channels and their order come from the devicetree (`zephyr,user` → `io-channels`). A `BUILD_ASSERT` in
`sensors.c` stops the build if that list and `enum sensor_channel` ever have different lengths.

### CAN

| Bus | Dir | ID | DBC message | Period | Content |
|---|---|---|---|---|---|
| CAN1 Autonomous | TX | 0x770 | `autonomous_t26` AQT7 | 50 ms | `REAR_BRK_PRESS`, 0.1 bar/bit |
| CAN1 Autonomous | RX | 0x710 | `autonomous_t26` AQT1 | — | Front brake pressure (`FRT_BRK_PRESS`), for the brake light |
| CAN2 DATA | TX | 0x770 | `data_t26` AQT7 | 125 ms | `SUSP_L`, `SUSP_R`, `NTC_1` (°C, 0–254; 255 = sensor fault) |

Both buses run at 1 Mbit/s (bit timing in the devicetree), retransmit until acknowledged and recover from
bus-off automatically.

**Bus health (`can_bus_service()`, port of `CAN_Service`).** `main` calls it every 100 ms. For each bus it:

- reads the state and the TEC/REC error counters,
- totals each protocol error type since boot (stuff, form, ACK, bit recessive, bit dominant, CRC, RX overrun;
  counted by the driver with `CONFIG_CAN_STATS`) and keeps the most recent type as `last_error`,
- counts bus-off entries and controller restarts,
- logs a change of state or of the last error type, at most once per second per bus, with the same
  explanations as the CubeIDE firmware, e.g.
  `DATA (CAN2) PASSIVE - TEC or REC >= 128: ... | TEC=136 REC=0 | last error: ACK - nobody acknowledged our frame: ...`,
- restarts a controller found stopped, at most every 100 ms (bus-off is left to the driver).

`can_bus_get_status(bus)` returns all of it as a `struct can_bus_status`; the debug snapshot shows it as
`acq7.can.autonomous` / `acq7.can.data`.

`can_send_frame()` never blocks: if every TX mailbox is busy, or the bus is off, the frame is dropped and counted
in `can_stats[bus].tx_dropped`; the next period sends a fresh value. `can_stats[]` also counts acknowledged
(`tx_ok`), failed (`tx_error`), received (`rx`) and lost (`rx_dropped`) frames per bus. Read it in the debugger.

**Receiving a new frame:** add `{CAN_BUS_DATA, DATA_T26_xxx_FRAME_ID}` (or `CAN_BUS_AUTONOMOUS`) to
`can_rx_ids[]` in `can_rx.c`, then a `case` in `can_handle_data_rx()` / `can_handle_autonomous_rx()` that
unpacks it with the DBC function and stores the value behind a getter. Each entry uses one hardware filter
(14 available).

**Sending a new frame:** add a `can_send_xxx()` encoder in `can_tx.c` that packs with the DBC function and calls
`can_send_frame()`, plus its own `next_xxx` deadline in `can_tx_thread()`.

### Debugging

**Log.** USART1, 115200 8N1. Besides start-up messages, CAN health changes and watchdog warnings, the debug
thread logs the sensor values every 100 ms, like `execute_100ms_tasks()` (illustrative values):

```
[00:00:05.100,000] <inf> debug: Rear brake 0.00 bar (adc 762) | Front brake 0.00 bar (coded 0, not arriving)
[00:00:05.100,000] <inf> debug: Susp L 0.00 mm (adc 2048) | Susp R 0.00 mm (adc 2051) | NTC1 24.8 C (adc 1210)
```

Set `CONFIG_AQT7_DEBUG_PRINT_MS=0` in `prj.conf` to turn it off, or e.g. `1000` for once per second.

**`acq7` snapshot.** `debug.c` refreshes the global `struct acq7_debug acq7` every 10 ms, with the same
layout as the CubeIDE `acq7`:

| Field | Contents |
|---|---|
| `time_ms` | Uptime |
| `adc.raw[4]`, `adc.filtered[4]`, `adc.volts[4]` | Per channel: latest sample, moving average, filtered value at the pin (V). Order: brake, susp L, susp R, NTC1 |
| `sensors.*` | Rear and front brake (bar), suspensions (mm), NTC1 (°C) |
| `io.brake_light`, `io.heartbeat` | Pin states. `brake_light` is logical: **1 = light on** (the CubeIDE one was the raw pin level, 0 = on) |
| `front.coded`, `front.alive`, `front.age_ms`, `front.rx_count` | 0x710 raw value, arriving within 500 ms, time since the last one, frames received |
| `can.tx.autonomous_aqt7`, `can.tx.data_aqt7` | Last payload queued on each bus |
| `can.autonomous`, `can.data` | `struct can_bus_status` of each bus: state, TEC/REC, error counts per type, last error, bus-off count, restarts, TX/RX counters |

To watch it while the firmware runs, add `acq7` to a live view that reads RAM over the ST-LINK without halting
the CPU: **CLion Live Watches** (embedded GDB server debug configuration), **STM32CubeIDE Live Expressions**
(debug configuration pointing at `build\zephyr\zephyr.elf`), or **STM32CubeMonitor** (load the ELF, plot
variables). Thread-local variables can't be watched this way; everything worth watching is in `acq7`.

To re-zero the brake sensor, read `acq7.adc.volts[0]` with the pedal released and copy it to `OFFSET_VOLTAGE`
in `conversions.c`.

### Differences from the STM32CubeIDE firmware

| | STM32CubeIDE | Zephyr |
|---|---|---|
| Moving average | 1 sample every 50 ms → ~500 ms window | 1 sample every 10 ms → 100 ms window (faster brake light) |
| Suspension zero | ~500 ms after boot | ~100 ms after boot |
| Brake light at boot | On until the first 50 ms task | Off |
| 0x710 decoding | Bytes 0–1, any length | DBC unpack, which needs **at least 3 bytes** (AQT1 in the DBC). If AQT1 sends 2 bytes, the front pressure stays 0 |
| Stale CAN frames | An older copy of the same ID still waiting in a mailbox is aborted | The new frame is dropped if the mailboxes are full |
| Watchdog | Fed by the main loop every 10 ms | Fed only while every thread checks in |
| CAN error types | Polled from the last error code register every 10 ms | Counted by the driver in the CAN error interrupt (`CONFIG_CAN_STATS`). On a bus with continuous errors (e.g. no other node: ACK error on every retransmission) this is one interrupt per error |
| CAN health check | Every 10 ms | Every 100 ms |
| `acq7.io.brake_light` | Raw pin level (0 = on) | Logical (1 = on) |

## Zephyr development setup

The Zephyr port is built with **west**, Zephyr's command-line tool. West works in a **workspace**: a folder
that holds this repository next to the Zephyr source and the modules it needs. This repository is the
workspace's *manifest repository*. Its `west.yml` pins the Zephyr version (**v4.5.0**) and the modules to
download (`cmsis_6`, `hal_stm32`), so every team member gets the same versions.

Only this repository is tracked in git. The rest of the workspace is downloaded by `west update` and must
never be committed:

```
<workspace>\                     <- e.g. D:\t26ws, NOT a git repository
├── .venv\                       <- Python virtual environment (per PC)
├── .west\                       <- created by west init (per PC)
├── T26_Acquisition_7\           <- this repository
├── zephyr\                      <- downloaded by west update
├── modules\                     <- downloaded by west update (hal_stm32, cmsis_6)
└── build\                       <- west build output
```

The commands below are for **Windows PowerShell**. On Linux or macOS, use `/` in paths and activate the
virtual environment with `source .venv/bin/activate`.

### 1. Install the host tools (once per PC)

Follow the "Install dependencies" step of the
[Zephyr Getting Started Guide](https://docs.zephyrproject.org/latest/develop/getting_started/index.html)
for your OS. On Windows:

```bash
winget install Kitware.CMake Ninja-build.Ninja oss-winget.gperf Python.Python.3.12 Git.Git oss-winget.dtc wget 7zip.7zip
```

Close and reopen the terminal afterwards, so it picks up the new `PATH`.

You also need the **Zephyr SDK 1.0.1** (the version required by Zephyr v4.5.0). It is installed once per PC
and shared by all workspaces. If you don't have it yet, install it in step 4 with `west sdk install`.

To flash the board you need an ST-LINK and its USB driver (included with STM32CubeIDE or STM32CubeProgrammer).

### 2. Create the workspace and clone the repository

Use a **short path**: Zephyr builds on Windows can fail with long paths.

```bash
mkdir D:\t26ws
```

```bash
cd D:\t26ws
```

```bash
git clone git@github.com:FSLART/T26_Acquisition_7.git
```

The Zephyr port is developed on the `zephyr_conversion` branch. Until it is merged into `main`, check it out:

```bash
git -C T26_Acquisition_7 checkout zephyr_conversion
```

### 3. Create the Python virtual environment and install west

```bash
py -3.12 -m venv .venv
```

```bash
.\.venv\Scripts\Activate.ps1
```

```bash
pip install west
```

If PowerShell refuses to run `Activate.ps1` ("running scripts is disabled on this system"), allow local
scripts for your user once, then activate again:

```bash
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

### 4. Initialise the workspace and download Zephyr

Run these from the workspace folder (`D:\t26ws`), with the virtual environment active (the prompt starts
with `(.venv)`). **Keep this order**: `west zephyr-export` needs the Python packages from step 4.3.

1. Initialise the workspace, using this repository's `west.yml`:

   ```bash
   west init -l T26_Acquisition_7
   ```

2. Download Zephyr and the modules (a few hundred MB):

   ```bash
   west update
   ```

3. Install Zephyr's Python requirements:

   ```bash
   pip install -r zephyr\scripts\requirements.txt
   ```

4. Register Zephyr with CMake:

   ```bash
   west zephyr-export
   ```

5. Only if the Zephyr SDK 1.0.1 isn't installed yet:

   ```bash
   west sdk install
   ```

### 5. Check the setup

Build the blinky sample for the Nucleo-F412ZG, which uses the same STM32F412 chip:

```bash
west build -b nucleo_f412zg zephyr\samples\basic\blinky -p
```

The setup works if the build ends with a memory usage table and creates `build\zephyr\zephyr.elf`.

### Build and flash the AQT7 firmware

Run from the workspace folder with the virtual environment active:

```bash
west build -b t26_aqt7 T26_Acquisition_7\zephyr_app -p
```

```bash
west flash
```

`-p` (pristine) deletes the previous build first. Leave it out for faster rebuilds of the same app.

`west flash` uses STM32CubeProgrammer over SWD with an ST-LINK. Its command-line tool must be on your `PATH`.
It is installed with STM32CubeCLT, so add this folder to your user `PATH` (adjust the version), then open a new
terminal:

```
C:\ST\STM32CubeCLT_1.23.0\STM32CubeProgrammer\bin
```

The log is on USART1 (PA9, 115200 8N1). A healthy start shows `IWDG running, 2000 ms timeout` and, about
100 ms later, `Suspension zeroed: ...`; the heartbeat (PC11) then toggles every 100 ms. See
[Zephyr firmware](#zephyr-firmware) for what the firmware does.

### The t26_aqt7 board

The board definition is in `zephyr_app/boards/t26/t26_aqt7/`. The pins and clocks are copied from
`T26_Acquisition_7.ioc`, which is only used as a reference: Zephyr doesn't use CubeMX or its generated code.

| File | Contents |
|---|---|
| `board.yml` | Board name and SoC (`stm32f412rx`) |
| `Kconfig.t26_aqt7` | Selects the SoC |
| `t26_aqt7.dts` | Devicetree: HSI → PLL 96 MHz, APB1 48 MHz, APB2 96 MHz; USART1 console; heartbeat (PC11, aliases `led0`/`heartbeat`) and brake light (PC10, active low, alias `brake-light`); CAN1 (PA11/PA12, alias `can-autonomous`, 75 % sample point) and CAN2 (PB12/PB13, alias `can-data`, 87.5 %), both 1 Mbit/s with RX pull-ups; ADC1 channels 7/8/9/14 (PA7, PB0, PB1, PC4), 12 bit, 480-cycle sampling, listed in `zephyr,user`; IWDG (alias `watchdog0`) |
| `t26_aqt7_defconfig` | Default Kconfig options for the board (MPU, console) |
| `board.cmake` | Flash runners: STM32CubeProgrammer (default, software reset) and J-Link |
| `t26_aqt7.yaml` | Board metadata for Zephyr's test runner (twister) |

Because `led0` points at the heartbeat, Zephyr's blinky sample runs on the board unmodified. This is a
quick way to check the clocks, the board files and flashing without the application:

```bash
west build -d build-blinky -b t26_aqt7 zephyr\samples\basic\blinky -p -- '-DBOARD_ROOT=D:/t26ws/T26_Acquisition_7/zephyr_app'
```

```bash
west flash -d build-blinky
```

`BOARD_ROOT` tells Zephyr where to find the board. `zephyr_app` adds it in its own `CMakeLists.txt`, so it's only
needed for builds outside `zephyr_app`. In PowerShell, keep the `-DBOARD_ROOT=...` argument in single quotes:
without them, PowerShell splits it at the drive letter's `:` and the build fails.

### Using CLion

Open the Zephyr app, not the workspace folder or the repository root. The workspace folder has no
`CMakeLists.txt` (and makes CLion index all of Zephyr), and a `CMakeLists.txt` at the repository root would be
for the STM32CubeIDE/HAL firmware.

1. **File → Open** → `D:\t26ws\T26_Acquisition_7\zephyr_app\CMakeLists.txt` → **Open as Project**.
2. **Tools → West → Change Project Root** → `D:\t26ws\T26_Acquisition_7`, so the whole repository (including
   `Core/DBC`) shows in the project tree and CLion's git integration sees it.
3. CLion recognises the folder as a **Zephyr West project**, so it's configured in the West settings, not the
   CMake settings (**Settings → Build, Execution, Deployment → West**, or the "Open West settings" link):

| Setting | Value |
|---|---|
| Toolchain | Use default (only CMake and Ninja are used from it; the compiler comes from the Zephyr SDK) |
| West executable | `D:\t26ws\.venv\Scripts\west.exe` |
| Board name | **Let CMake decide** |
| Build directory | Outside the repository, e.g. `D:\t26ws\build-clion` |

**Board name:** `t26_aqt7` isn't in CLion's board list, because the list only contains Zephyr's own boards.
Leave it on "Let CMake decide", and set the workspace's default board once (from the workspace folder, with
the virtual environment active):

```bash
west config build.board t26_aqt7
```

CLion then runs `west build` without `-b`, and west uses this default. This setting is required: without it,
west refuses to reuse an existing build folder ("Cached board not defined"). It is stored in the workspace's
`.west\config`, so each team member runs it once. `zephyr_app/CMakeLists.txt` also defaults to `t26_aqt7`, as
a fallback.

**Build directory:** a relative path like `build` is created inside the repository. Use an absolute path
outside it, so build output never ends up in git.

Using the virtual environment's `west.exe` also makes the build use its Python, which has Zephyr's
requirements installed. You don't need to set `ZEPHYR_BASE`: `west zephyr-export` already registered Zephyr
with CMake.

```

After pulling changes, run `west update` again. It downloads a new Zephyr version if someone changed

```

```bash

```

### Troubleshooting

| Error | Cause | Fix |
|---|---|---|
| `west` is not recognized | Virtual environment not active | Activate `.venv` (see [Every new terminal](#every-new-terminal)) |
| `ModuleNotFoundError: No module named 'jsonschema'` (or another module) on `west zephyr-export` / `west build` | Zephyr's Python requirements are missing | Run step 4.3, then try again |
| `CMake is not installed or cannot be found; cannot build.` | The terminal was opened before CMake was added to `PATH` | Open a new terminal, or reload `PATH` with the command below, then activate `.venv` again |
| `running scripts is disabled on this system` | PowerShell execution policy | See step 3 |
| `BOARD_ROOT element without a 'boards' subdirectory` / board `t26_aqt7` not found, and the command shows `D: /...` | PowerShell split `-DBOARD_ROOT=D:/...` at the `:` | Put the argument in single quotes |
| `Cached board not defined, please provide it` | The build folder exists but has no board (e.g. an earlier configure failed) | Run `west config build.board t26_aqt7`, delete the build folder, build again |
| `west flash` can't find `STM32_Programmer_CLI` | STM32CubeProgrammer not on `PATH` | See [Build and flash the AQT7 firmware](#build-and-flash-the-aqt7-firmware) |

To reload `PATH` in the current PowerShell terminal:

```bash
$env:Path = [Environment]::GetEnvironmentVariable('Path','Machine') + ';' + [Environment]::GetEnvironmentVariable('Path','User')
```

STM32CubeCLT also installs CMake and Ninja. If it comes first in your `PATH`, those copies are used. That
works, but `cmake --version` shows the CubeCLT version.
